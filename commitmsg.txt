trusted_click: input the browser itself produced — 1:1 with a real mouse, still in the background

Ali: "verify and register exactly how a human click is registered in the website code and simulate
it in code background and implement when you find something that works 1:1 identical".

★ THE MEASUREMENT, NOT AN OPINION. bench/click_fingerprint.html attaches a capture-phase listener
for every pointer/mouse/focus event and records the FULL property set of each one, plus the side
state a site can read at that instant (activeElement, :hover, computed style, and whether the
default action has already run). tools/click-fingerprint.mjs then runs the same four clicks — a
button, a checkbox, a link, an input — through both paths and diffs the two records field by field,
with the page's own JS as the oracle.

MEASURED — what the two paths actually put in front of the page:
                        click (dispatchEvent)        trusted_click (Input.dispatchMouseEvent)
  click.isTrusted       false                        true
  click.detail          0                            1
  click.clientX/Y       0 / 0                        the real point (83,147)
  pointermove/mousemove absent before the press      present, as a mouse does
  event sequence        adds pointerenter/mouseenter exactly the browser's own sequence
                        (visible to capture listeners)
  default action        RUNS                         RUNS
★ AND THAT LAST ROW CORRECTED ME. I had already written into the guide that the synthetic path
"cannot toggle a checkbox, follow a link or submit a form". Measured: it does all three — click
finishes with HTMLElement.click(), which performs activation behaviour. The guide now says what is
true (and says that I had it wrong), because a doc that overstates the gap is the same kind of
fault as one that overstates the capability.

★ THE HARD PART WAS NOT THE DISPATCH — IT WAS THAT THE BROWSER DROPS IT.
First version, on a background tab: mouseMoved took 5,080ms to return and the PRESS VANISHED. The
page recorded pointerover>pointermove and no pointerdown/mousedown/click at all — a "trusted" click
that did nothing while its transport envelope said success. The cause is that the tab was not
visible: the page reported document.visibilityState:'hidden', and Chrome throttles a hidden
renderer and drops input into it.
FIXED with two protocol calls that make the renderer behave as a focused, active page WITHOUT
bringing it to the front:
    Emulation.setFocusEmulationEnabled(true)   // "simulates a focused and active page"
    Page.setWebLifecycleState('active')        // lifts the frozen/idle lifecycle
Same click afterwards: 151ms, and the page records isTrusted:true, detail:1, clientX:83, with the
default action firing on ALL FOUR elements — verified, not assumed. The tab stayed in the
background; the user's active tab was never touched.
★ Also fixed on the way: move→press→release in the same tick gets coalesced away, so there is a
gap between arriving and pressing — real timing, which is part of what makes a click a click.

★ ROUTING. chrome.debugger exists only in the service worker and the SW is not itself a WS client,
so the op takes three layers: hub SW_REQUIRED_OPS (route to the relay), offscreen case (FORWARD it
to the SW — the relay has no debugger API), SW handleTabControl (do it). All three are asserted by
a test, because the first attempt silently answered "Unknown action type: trusted_click" INSIDE a
success envelope while the page saw nothing. That produced a second fix, general:
relayFailure(payload) — an error riding inside a successful envelope must never read as a result.

★ COST, measured: ~2-3ms to attach (REUSED for 25s via __dbgKeepAlive, so a burst of clicks pays it
once) and ~140-990ms per click, most of it the page's own handling. Chrome shows its "debugging
this browser" infobar while attached and the attachment is released on a timer.

★ RESEARCH THAT SHAPED IT (Ali asked me to look at what comparable tools do): the canonical field
list a real mouse input carries is the CDP Input.setMouseEvent parameter set — button, buttons
(Left=1), clickCount, force, pointerType, x/y, modifiers, timestamp — taken from the protocol
source (chromedp/cdproto). Puppeteer and Playwright route clicks through that same pipeline, which
is why their clicks are trusted; what they do NOT do is solve the background case without
activating the tab. Our emulation calls are what let the same fidelity exist in a tab the user
cannot see, which is the property WebSense is built around.
