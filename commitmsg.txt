four bugs found by simulating real tasks on 7 live pages

Ali: "restart and properly test, simulate a few tasks on a sample of 5-7
different pages as you did before and fix issues". The sweep: browse -> find ->
page_slice -> type -> scroll -> read the auto-DIFF, on bbc.com/news,
books.toscrape, developer.mozilla.org, old.reddit.com, stripe.com/pricing,
news.ycombinator.com and x.com/home. Every fix below was found by USING the
tools, not reading them, and each is pinned by a test. 159 tests pass.

★ 1. page_slice{indices:[i]} RETURNED THE WHOLE PAGE.
`indices` was never declared in page_slice's schema, so it was stripped before
the handler saw it — while the handler forwards its args straight to
sliceSnapshot(), which has supported `indices` since the DIFF was built, and the
DIFF block tells the model that this exact call is how you pull the detail for
an index it named. Measured: page_slice{indices:[31]} returned 543 of 543
records on books.toscrape. The documented follow-up silently undid the
index/diff split. Fixed, and the guard is now GENERAL instead of one-tool: the
new test takes the key set from sliceSnapshot itself and checks every tool that
forwards to it (find was already covered; page_slice was not).

★ 2. "Element not found" FOR AN ELEMENT THAT WAS RIGHT THERE — three causes.
Found on bbc.com/news's search field and x.com's file input:
  (a) locatorOf returned '#' + id. React's useId mints ids like ":R35tbdm:", and
      a colon starts a pseudo-class, so the locator was invalid CSS.
  (b) CSS.escape was then applied to attribute VALUES, which OVER-escapes inside
      a quoted value, and the emitted backslashes do not survive this pipeline:
      probed in-page, querySelector received '#:R35tbdm:' — escape eaten —
      and threw "not a valid selector" while getElementById(':R35tbdm:') worked.
  (c) resolveSelectorRef rejected any ref containing a character outside a
      hand-rolled whitelist that OMITS '/' — so every href/src locator, and
      x.com's input[accept="image/jpeg,image/png,..."], returned null before
      querySelector ever ran.
Now: a clean id is used exactly as before; an id needing escaping only wins when
nothing better exists; attribute values are quote-escaped (only " and \), built
with fromCharCode(92) because the collector is a template literal; and the
whitelist is gone — the CSS parser is the judge, invalid selectors throw and are
caught, which is what the whitelist was hand-rolling minus the false negatives.
Verified live: input[id=":R35tbdm:"] resolves where every backslash-bearing form
does not, and x.com's file input now resolves.

★ 3. A STATIC PAGE REPORTED mutated:true FOREVER.
The diff baseline was keyed by locator alone. On news.ycombinator.com all 30
story rows carry the same locator (locatorOf walks at most 5 ancestors), so
later entries overwrote earlier ones and 29 rows were compared against ONE
arbitrary baseline record. Measured: every diff reported the same 29
"content changed" entries (wasNameLen 6 vs nameLen 12-25) so a pure scroll came
back mutated:true, and a second identical scroll reported the identical 29 —
permanent, not a settle artefact. Cause confirmed by dumping the group.
Now keyed by locator PLUS THE ORDINAL WITHIN IT (the k-th element carrying a
locator matches the k-th baseline element carrying it): one-to-one, still stable
when elements appear under a different locator. All 7 sample pages now report
mutated:false, structure 0, content 0 on a pure scroll, with the scroll in the
viewport group where it belongs. Previously 5 of 7 reported mutated:true.

★ 4. A FALSE SUCCESS: a refused action reported as confirmed.
Hub replies are {type,id,success,data:{…}} and the top-level success means "a
reply was delivered", NEVER "the action worked". type_text judged from the
envelope, so on bbc.com/news a type into a disabled input came back
effect:'confirmed' while its own payload said {success:false, reason:'the target
is disabled'} and the auto-DIFF for the same call said mutated:false — "treat
this action as NOT LANDED". Two signals disagreed and the optimistic one was
wrong. classifyEffect has known this since 2026-09-25; the fix is the same
unwrap, now a single shared unwrapRelay() so the next handler cannot miss it.

★ 5. GUIDANCE THAT LOOPS. A target that cannot accept text now names why and
what to do instead of advising "re-read the field and re-type" — measured:
bbc's search input is disabled until its menu opens, and x.com's is a file
input. Both now answer enable_then_type / form{action:"upload"} respectively.

Also carried from this round, unchanged: the regions grouping (name + shape,
grouped by identity) and the reverted name-only variant stay as they were.
